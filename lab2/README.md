# Лабораторная работа №2. Микросервисный интернет-магазин «Libraria»

## 1. Описание проекта

Книжный интернет-магазин на **8 независимых backend-сервисах** + API Gateway. Покупатель регистрируется, ищет книги
в каталоге, складывает их в корзину и оформляет заказ; оформление проходит **сагу** через склад и оплату, а покупатель
видит её шаги в реальном времени. Администратор отправляет и доставляет заказы, пополняет склад, видит выручку.

Оплата **имитируется**: при оформлении выбирается тестовый способ (карта «успешно», карта «отказ», оплата при получении).
Реальные платёжные данные не запрашиваются и не обрабатываются.

## 2. Архитектура

```text
                         Покупатель / администратор (браузер)
                                        │  HTTP :8088
                                ┌───────▼───────┐
                                │  API Gateway  │  JWT, роли, rate limit, request-id,
                                └───────┬───────┘  агрегация каталог + склад, /api/status
   ┌──────────┬──────────┬──────────┬───┴──────┬──────────┬──────────┬──────────────┐
   ▼          ▼          ▼          ▼          ▼          ▼          ▼              ▼
 auth       user      catalog   inventory    cart      order     payment     notification
   │          │          │          │      REST│◄──────────┤REST      │              │
   │          │          │          │   cart → catalog    order → cart              │
   ▼          ▼          ▼          ▼          ▼          ▼          ▼              ▼
auth_db   user_db   catalog_db inventory_db cart_db   order_db  payment_db  notification_db
   │          │          │          │          │          │          │              │
   └──────────┴──────────┴──── RabbitMQ: exchange shop.events (topic) ──────────────┘
          у сервисов-издателей — transactional outbox в собственной базе
```

| Сервис | Ответственность | Данные | Публикует | Слушает |
| --- | --- | --- | --- | --- |
| **auth** | регистрация, вход, JWT, роли | auth_db | `user.registered` | — |
| **user** | профиль покупателя, адрес доставки | user_db | — | `user.registered` |
| **catalog** | книги, жанры, поиск, цены | catalog_db | `book.created` | — |
| **inventory** | остатки, резерв под заказ | inventory_db | `inventory.reserved` / `inventory.rejected` | `book.created`, `order.created`, `order.paid`, `order.cancelled` |
| **cart** | корзина покупателя | cart_db | — | `order.paid` |
| **order** | заказы, статусы, сага оформления | order_db | `order.created`, `payment.requested`, `order.paid`, `order.cancelled`, `order.shipped`, `order.delivered` | `inventory.*`, `payment.*` |
| **payment** | платежи (имитация провайдера) | payment_db | `payment.succeeded` / `payment.failed` | `payment.requested` |
| **notification** | уведомления в приложении | notification_db | — | `user.registered`, `order.*` |
| API Gateway | единая точка входа (не бизнес-сервис) | — | — | — |

### Почему так разделено

* **catalog и inventory**: каталог читают постоянно и много (поиск, карточки), остатки меняются при каждом заказе
  и требуют блокировок. Разделение позволяет масштабировать чтение каталога, не трогая склад, и не держать
  блокировки на таблице, которую читает поиск.
* **order отдельно от payment**: оплата — внешний и медленный шаг (провайдер отвечает ~1 с); заказ хранит только
  состояние саги. Смена платёжного провайдера не затрагивает заказы.
* **cart отдельно от order**: корзина — черновик, который часто меняется; заказ — неизменяемый документ с ценами
  на момент покупки (`OrderItem` копирует название и цену).
* **auth отдельно от user**: хеши паролей изолированы от профилей и адресов.
* **notification только на событиях**: отказ уведомлений никогда не мешает оформить заказ.

### Базы данных

Database-per-service: **8 баз, у каждого сервиса свой логин**, который видит только свою базу
(`infrastructure/postgres/init-databases.sh`). Физически они на одном сервере PostgreSQL — компромисс для ноутбука;
изоляция обеспечена правами, вынос базы на отдельный сервер меняет только `DATABASE_URL`.
Связи между данными сервисов — только по идентификаторам (`user_id`, `book_id`, `order_id`), без внешних ключей между базами.

## 3. Сага оформления заказа

Хореография: ни один сервис не вызывает следующий напрямую, каждый реагирует на событие предыдущего.
order-service хранит конечный автомат; переход выполняется **только из ожидаемого состояния**, поэтому дубликаты и
запоздавшие события игнорируются.

```text
 POST /orders ─► order: pending ──order.created──► inventory: резерв всех позиций (всё или ничего)
                                                     │
          ┌───────── inventory.rejected ◄────────────┤ не хватает ─► order: cancelled (out_of_stock)
          │                                          │
          │          inventory.reserved ◄────────────┘ хватает
          ▼
 order: awaiting_payment ──payment.requested──► payment: «провайдер»
          ┌──────── payment.failed ◄─────────────────┤ карта отклонена
          │   order: cancelled (payment_declined) ──order.cancelled──► inventory: снимает резерв  (компенсация)
          │
          └──────── payment.succeeded ◄──────────────┘ успешно / оплата при получении
 order: paid | confirmed ──order.paid──► inventory: резерв → продано; cart: убирает купленное; notification
 admin: shipped ──► delivered  (order.shipped / order.delivered → notification)
```

Ключевые решения:

* **Резерв «всё или ничего»**: в одной транзакции по каждой позиции выполняется условный
  `UPDATE stock SET available = available - q WHERE available >= q`. Если хоть одна строка не обновилась — откат.
  Это же исключает гонку за последний экземпляр: двое покупателей не могут получить одну книгу (покрыто тестом).
* **Компенсация**: при отказе карты order публикует `order.cancelled`, и склад возвращает резерв.
* **Отмена покупателем** возможна до оплаты картой (`pending`) и для заказов с оплатой при получении (`confirmed`) —
  проданные, но не отправленные книги возвращаются на склад. Оплаченный картой заказ отменить нельзя (409):
  в имитации провайдера нет возвратов.
* **Корзина очищается по `order.paid`, а не при оформлении**: если карта отклонена, книги остаются в корзине.
* **Идемпотентность оформления**: клиент передаёт заголовок `Idempotency-Key`; повторный запрос (двойной клик,
  повтор при сбое сети) возвращает тот же заказ, второй не создаётся.
* **Цена фиксируется в заказе**: позиции копируют название и цену на момент покупки.

## 4. Надёжность событий: transactional outbox

Первый запуск показал проблему: catalog-service опубликовал `book.created`, пока RabbitMQ ещё поднимался, и после
трёх попыток событие было **потеряно** — у книги «Ion» не появилось остатка на складе.

Решение — **Transactional Outbox** (`common/utm_common/outbox.py`): событие записывается в таблицу `outbox`
**той же базы и в той же транзакции**, что и изменение данных (книга, заказ, платёж, резерв). Либо сохраняется
и то и другое, либо ничего. Фоновый поток (relay) отправляет неотправленные строки в RabbitMQ по порядку и помечает их;
пока брокер недоступен, строки ждут. Гарантия — доставка «хотя бы один раз», поэтому все обработчики идемпотентны.
После внедрения: 30 из 30 книг получают остатки при любом порядке запуска контейнеров.

Дополнительно вся схема очередей (`TOPOLOGY` в `events.py`) объявляется и издателями, и потребителями: событие,
опубликованное раньше первого запуска потребителя, попадает в его очередь, а не теряется.

## 5. Технологии

| Что | Выбор | Почему |
| --- | --- | --- |
| Сервисы | Python 3.12 + FastAPI | быстрый REST, OpenAPI/Swagger генерируется автоматически, валидация через Pydantic |
| БД | PostgreSQL 16 | транзакции и условные UPDATE для резервирования; отдельная база на сервис |
| ORM | SQLAlchemy 2 | одна модель данных для PostgreSQL и SQLite в тестах |
| Брокер | RabbitMQ 3.13 | очередь на каждого потребителя, подтверждения, переживает перезапуск потребителя; Kafka избыточна для такого объёма |
| Аутентификация | JWT (HS256), пароли — scrypt | токен проверяется в gateway без обращения к auth-service |
| Деньги | целые числа (bani) | без ошибок округления float |
| Запуск | Docker Compose | вся система одной командой |
| Витрина | HTML/CSS/JS без фреймворков | раздаётся gateway; не считается микросервисом |

## 8. API (через gateway)

Полная документация — Swagger `/docs` у gateway и у каждого сервиса.

| Метод и путь | Доступ | Сервис |
| --- | --- | --- |
| `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me` | все / вошедшие | auth |
| `GET /api/users/me`, `PATCH /api/users/me` | вошедшие | user |
| `GET /api/books?q=&genre=&sort=`, `GET /api/books/{id}` | все | catalog **+ inventory (агрегация)** |
| `GET /api/genres` | все | catalog |
| `GET /api/cart`, `PUT /api/cart/items/{book_id}`, `DELETE /api/cart/items/{book_id}` | вошедшие | cart |
| `POST /api/orders` (+ `Idempotency-Key`) | вошедшие | order |
| `GET /api/orders`, `GET /api/orders/{id}`, `POST /api/orders/{id}/cancel` | вошедшие | order |
| `GET /api/orders/{id}/payment` | вошедшие | payment |
| `GET /api/notifications`, `POST /api/notifications/{id}/read` | вошедшие | notification |
| `POST /api/admin/books`, `PATCH /api/admin/books/{id}` | admin | catalog |
| `PUT /api/admin/stock/{book_id}` | admin | inventory |
| `GET /api/admin/orders`, `GET /api/admin/stats`, `POST /api/admin/orders/{id}/ship`, `.../deliver` | admin | order |
| `GET /api/status`; `GET /health`, `GET /ready` у каждого сервиса | все | — |

**Агрегация в gateway:** `GET /api/books` берёт книги из catalog и остатки из inventory одним запросом `/stock?ids=…`.
Если inventory недоступен, каталог всё равно отдаётся, а наличие помечается «неизвестно» (graceful degradation,
витрина показывает плашку).

## 9. Авторизация, ошибки, логи

* Пароль — scrypt-хеш с солью; JWT содержит `sub`, `role`, `exp`. Gateway проверяет токен один раз и передаёт
  сервисам `X-User-Id` / `X-User-Role`; такие заголовки от клиента **всегда отбрасываются** (покрыто тестом).
  Наружу открыт только gateway (:8088) и консоль RabbitMQ. Роли: `customer`, `admin`; чужой заказ — 404.
* Единый формат ошибки `{"error": {"code", "message", "request_id", "details?"}}`; 422 по полям, 404, 401/403,
  409 (недопустимый переход статуса, повторный e-mail), 400 (пустая корзина), 503/504 при недоступном или медленном
  сервисе; stack trace — только в логах.
* Логи — JSON (timestamp, service, level, request_id, message + поля). `request_id` создаётся в gateway и передаётся
  в заголовках и **внутри событий**, поэтому весь путь заказа виден одной командой:

```bash
docker compose logs | grep <request_id>
```

### Найденные и исправленные проблемы

* **Потеря события при старте** → transactional outbox + строгая проверка готовности RabbitMQ (`check_port_connectivity`).
* **Отменённый заказ с оплатой при получении не возвращал книги** (они уже были «проданы») → отмена возвращает и
  зарезервированные, и проданные позиции.
* **Корзина очищалась при оформлении**, и после отказа карты покупатель терял её → очистка по `order.paid`.
* **Старая привязка очереди** (`cart ← order.created`) оставалась в RabbitMQ, потому что её объявляли сервисы со старой
  версией общей библиотеки → после изменения общего кода пересобираются все сервисы.
* **Порт 8080 занят** другим dev-сервером (Flutter) → gateway опубликован на 8088.

## 12. Выводы

1. Магазин естественно делится по **данным и согласованности**: каталог (много чтения), склад (конкурентные изменения),
   заказ (состояние процесса), платёж (внешняя интеграция).
2. **Распределённая транзакция заменена сагой** с компенсацией. Цена — eventual consistency: заказ несколько сотен
   миллисекунд находится в промежуточных статусах, и интерфейс показывает это пользователю, а не скрывает.
3. **«Сохранить, потом опубликовать» теряет события** — это проявилось на практике и решается outbox'ом в той же транзакции.
4. **Идемпотентность нужна на каждом уровне**: ключ оформления от клиента, уникальный платёж на заказ, переходы
   из ожидаемого состояния, проверки id событий у потребителей.
5. Ограничения: rate limit в памяти gateway (при нескольких репликах нужен Redis); платёжный провайдер — имитация без
   возвратов; базы на одном сервере PostgreSQL. Stateless gateway и все сервисы (состояние — в PostgreSQL)
   масштабируются горизонтально — это используется в ЛР3.
