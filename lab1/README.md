# Лабораторная работа №1. RAG-система по материалам UTM / FCIM

## 1. Описание проекта

Вопросно-ответная система для студентов Технического университета Молдовы. Она отвечает на вопросы
о регламентах (оценивание, ECTS, стипендии, антиплагиат), устройстве университета и факультета FCIM,
программах обмена и т. д., **только на основании документов с сайтов utm.md и fcim.utm.md**, с указанием
источников, и честно отказывается отвечать, если информации в базе нет.

Предметная область выбрана потому, что:

* корпус реальный и «грязный»: HTML-страницы, новости и PDF-регламенты на трёх языках (ro / en / ru);
* документы регулярно обновляются — есть смысл в инкрементальном grabber'е;
* по ним легко составить проверяемые вопросы с однозначными ответами (числа, сроки, имена).

## 2. Архитектура

```text
 utm.md / fcim.utm.md (WordPress REST API: pages, posts, media PDF)
          │
          ▼
 ┌──────────────────┐   SQLite manifest: modified + sha256 текста
 │ Grabber          │── новые / изменённые / удалённые / дубликаты
 └────────┬─────────┘
          ▼ data/raw/*.json (+ .pdf)
 ┌──────────────────┐
 │ Preprocessing    │  HTML → текст с заголовками, PDF → склейка строк/переносов,
 │                  │  нормализация диакритики ş→ș, удаление boilerplate
 └────────┬─────────┘
          ▼ data/processed/documents.jsonl
 ┌──────────────────┐
 │ Chunking         │  fixed | overlap | paragraph | heading (title + путь секции)
 └────────┬─────────┘
          ▼
 ┌──────────────────┐
 │ Embeddings       │  intfloat/multilingual-e5-small (384), префиксы query:/passage:
 └────────┬─────────┘
          ▼
 ┌──────────────────┐
 │ Vector store     │  Chroma (HNSW, cosine), metadata: url, title, lang, section, ...
 └────────┬─────────┘
   question│
          ▼
 Retriever top-K=20 → Filters (cosine ≥ 0.75, длина, дедупликация, ≤2 chunk на документ)
          ▼
 Reranker cross-encoder mmarco-mMiniLMv2 → top-5, score ≥ 0
          ▼                       └── пусто → отказ без вызова LLM
 LLM (Ollama, qwen2.5:3b) + strict prompt → ответ с цитатами [n] + список источников
```

## 3. Используемые технологии

| Компонент | Выбор | Почему |
| --- | --- | --- |
| Сбор данных | `requests` + WordPress REST API | оба сайта на WordPress: `/wp-json/wp/v2/` отдаёт id, ссылку, `modified` и контент без меню/сайдбаров, можно запрашивать только изменённое |
| PDF | `pypdf` | чистый Python, достаточно для текстовых PDF; сканы без текстового слоя отбрасываются с ошибкой в manifest |
| HTML | `BeautifulSoup` + `lxml` | сохраняем заголовки `h1–h4` как `#`, нужны для heading-chunking |
| Embeddings | `sentence-transformers`, multilingual-e5-small / e5-base, paraphrase-multilingual-MiniLM | корпус на 3 языках, вопросы задаются на любом из них — нужны многоязычные модели |
| Vector DB | Chroma (embedded, persistent) | хранит metadata рядом с векторами и фильтрует по ним в запросе (`lang`, `source`), не требует отдельного сервера; на ~8 тыс. chunks HNSW более чем достаточно. FAISS потребовал бы отдельного хранилища metadata |
| Reranker | `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` | многоязычный cross-encoder (обучен на mMARCO, 14 языков), 118M параметров — работает на CPU |
| LLM | Ollama: `qwen2.5:3b`, `llama3.2:3b` | бесплатно, локально, 3B помещаются в 16 GB RAM без GPU |
| Оценка | собственные метрики + pandas | см. раздел Evaluation |

## 4. Установка

Требуется Python 3.11+ и [Ollama](https://ollama.com).

```bash

.venv\Scripts\activate          # Linux/macOS: source .venv/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cpu      # или .../whl/cu126 для NVIDIA GPU
pip install -r lab1/requirements.txt
ollama pull qwen2.5:3b

```

## 5. Запуск

Все команды из папки `lab1/`:

```bash
python -m src.cli grab                 # собрать/обновить документы (повторный запуск качает только изменения)
python -m src.cli index                # очистка, chunking, embeddings, запись в Chroma
python -m src.cli ask "Câte ore de muncă corespund unui credit ECTS?"
python -m src.cli ask "Кто является ректором UTM?" --json
python -m src.cli eval                 # метрики на 38 вопросах
python -m src.cli eval --no-generation # только retrieval (без LLM, быстро)
python -m src.cli experiments          # все эксперименты → experiments/results/REPORT.md
python -m src.cli experiments --resume # продолжить прерванный запуск, готовые варианты не пересчитываются
python -m src.evaluation.validate_questions
pytest
```

### Веб-интерфейс

```bash
python -m src.cli serve                # затем открыть http://127.0.0.1:8000
```

Одностраничный интерфейс поверх того же pipeline (`app/server.py` — FastAPI, `app/static/` — HTML/CSS/JS без фреймворков
и внешних зависимостей):

* вопрос на ro / en / ru, ответ со ссылками `[n]`; клик по ссылке подсвечивает карточку источника;
* карточки источников: документ, сайт и раздел, исходный фрагмент текста (раскрывается) и ссылка на оригинал;
* строка «как найден ответ»: сколько фрагментов найдено → прошло фильтры → попало в контекст модели, время ответа;
* отдельное состояние «в базе нет ответа» и ошибка с кнопкой повтора, если не запущена Ollama;
* светлая и тёмная тема по настройке системы, адаптивная вёрстка, уважение к `prefers-reduced-motion`.

API: `POST /api/ask {"question": "..."}` → ответ, флаг отказа, источники и статистика pipeline; `GET /api/info` — размер корпуса и модели.
Это же API станет одним из сервисов в лабораторной работе №2.

## 6. Configuration

Все параметры — в [`configs/default.yaml`](configs/default.yaml). Любой ключ можно переопределить из командной строки:

```bash
python -m src.cli --set retrieval.top_k=10 --set reranker.enabled=false eval --no-generation
python -m src.cli --set generation.model=llama3.2:3b ask "..."
```

`embeddings.device: auto` — embedding-модель и reranker работают на GPU, если установлен torch с CUDA, иначе на CPU.
На CPU (i7-12700H) построение одного индекса (~8 000 chunks, e5-small) занимает 10–14 минут, поэтому группы
экспериментов 1–4 удобнее запускать на GPU; `--resume` позволяет переключиться посреди прогона.

Для каждой комбинации (стратегия chunking, размер, overlap, embedding-модель) создаётся своя коллекция Chroma,
поэтому эксперименты переключаются между индексами без пересборки. Индекс пересобирается автоматически,
если изменился корпус (fingerprint от id и текста документов).

## 7. Компоненты подробно

### 7.1 Grabber

* **Источник**: WordPress REST API двух сайтов — все страницы (`pages`), 300 последних изменённых новостей (`posts`)
  с каждого сайта, нормативные PDF из медиатеки.
* **Отбор PDF**: из ~9 000 PDF берутся только регламенты/гиды (ключевые слова `regulament`, `ghid`, `metodologie`, `carta`, ...),
  исключаются расписания, CV, приказы — это таблицы и персональные данные, которые только шумят. До 60 файлов на сайт, ≤ 25 MB.
* **Инкрементальность**: сначала лёгкий listing (`id`, `modified`), полный контент запрашивается (`include=...`)
  только для новых и изменённых id. В SQLite-manifest хранится `modified` и sha256 нормализованного текста:
  если дата изменилась, а текст нет — файл не перезаписывается.
* **Дубликаты**: документ с тем же хешем текста, что у уже сохранённого (новость на обоих сайтах, повторно загруженный PDF),
  помечается `duplicate` и в корпус не попадает.
* **Удаления**: страница, исчезнувшая из полного listing, помечается `deleted`.
* **Ошибки**: retry с экспоненциальной паузой на 429/5xx/timeout, ошибка одного документа записывается в manifest
  (`status=error`) и не останавливает сбор; при следующем запуске такой документ пробуется снова.

Результаты запусков (таблица `runs` в manifest):

| Запуск | new | updated | unchanged | duplicates | deleted | errors |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 — первый сбор | 908 | 0 | 0 | 30 | 0 | 4 |
| 2 — лимит PDF поднят до 25 MB | 1 | 0 | 938 | 0 | 0 | 3 |
| 3 — исключены CV (`vitae`, `europass`) | 0 | 0 | 935 | 0 | 2 | 3 |

Три оставшиеся ошибки — сканированные PDF без текстового слоя (нужен OCR, вне рамок работы).

Итоговый корпус: **876 документов** (после отсева страниц короче 300 символов: слайдеры, «test», пустые лендинги).

| Сайт | page | post | pdf |
| --- | ---: | ---: | ---: |
| utm.md | 133 (ro 65, en 34, ru 34) | 291 | 50 |
| fcim.utm.md | 97 (ro 54, en 43) | 298 | 7 |

### 7.2 Обработка данных

* HTML: удаляются `script/style/nav/footer/form/iframe`, заголовки сохраняются как `#`/`##`, списки как `- `,
  вложенные блоки не дублируются.
* PDF: склейка переносов `regula-\nment`, склейка строк, разорванных вёрсткой, удаление номеров страниц,
  статьи `Art. 5`, `Capitolul II` превращаются в заголовки — чтобы heading-chunking работал и для регламентов.
* Нормализация: NFC, румынская диакритика с седилью `ş ţ` → `ș ț` (на сайтах встречаются оба варианта,
  а для embedding-модели это разные токены), неразрывные пробелы, лишние переводы строк.
* Boilerplate: «Distribuie», «Citește mai mult», «Descarcă» и т. п.
* Metadata каждого chunk: `document_id, source, doc_type, url, title, lang, updated_at, section, chunk_index`.

Найденная проблема: в одном PDF (регламент о стипендиях 2026, `utm:pdf:207103`) шрифт без корректной таблицы
Unicode — `ă` извлекается как `6`, `ț` как `{`. Retrieval по нему всё равно работает за счёт остальных слов,
а в корпусе есть предыдущая редакция того же регламента с нормальным текстом.

### 7.3 Защита от hallucination

1. Если после фильтров и reranker не осталось ни одного chunk (score ниже −3) — LLM не вызывается, возвращается
   фиксированная фраза отказа на языке вопроса и список похожих документов базы. Если score между −3 и 0 —
   ответ формируется, но помечается как «низкая уверенность» (см. 10.10).
2. Strict prompt: использовать только пронумерованный контекст, цитировать `[n]`, при отсутствии ответа —
   дословная фраза отказа.
3. В ответе всегда выводится список источников (URL), на основании которых он сформирован.

## 8. Evaluation

### Набор вопросов

[`data/eval/questions.jsonl`](data/eval/questions.jsonl) — **38 вопросов**:

| Тип | Кол-во | Пример |
| --- | ---: | --- |
| factoid | 13 | «În ce an a fost fondată UTM?» |
| specific | 10 | «La câte discipline pe an se poate mări nota?» |
| contextual | 5 | «What documents must a student prepare before an Erasmus+ mobility?» |
| multi_doc | 3 | «Cine conduce UTM și cine conduce FCIM?» |
| unanswerable | 7 | «What is the Wi-Fi password in the UTM library?» |

Языки: ro 24, en 9, ru 5. Часть вопросов кросс-языковые: вопрос на английском, ответ только в румынском документе (q21, q27).

Для каждого вопроса указаны эталонный ответ, ключевые факты (`keywords`, допускаются варианты `4|four`)
и `relevant_docs` — все документы, где есть ответ (включая переводы страницы на en/ru).
Скрипт `validate_questions` проверяет, что каждый ключевой факт действительно есть в указанных документах,
и подсказывает другие документы, содержащие все ключевые слова, — так были найдены и добавлены пропущенные
релевантные документы (контакты на en/ru, страница Совета FCIM со списком департаментов).

### Метрики и почему именно они

Релевантность — на уровне документа: список chunks сворачивается в список уникальных документов.

| Метрика | Что показывает |
| --- | --- |
| Hit@K | есть ли хотя бы один релевантный документ в top-K — главное для RAG: LLM нужен хотя бы один источник с ответом |
| Recall@K | доля всех релевантных документов в top-K — важна для multi_doc |
| MRR | насколько высоко первый релевантный документ — влияет на то, попадёт ли он в ограниченный контекст |
| Precision@K | доля мусора в контексте |
| ctx_hit / ctx_mrr | то же, но для **итогового контекста LLM** (после фильтров и reranker) |
| unanswerable_ctx_empty | доля вопросов вне базы, для которых фильтры не пропустили ни одного chunk |
| keyword_recall | доля ключевых фактов эталона, присутствующих в ответе (детерминированная замена «correctness») |
| refusal_accuracy, false/correct refusal rate | отказ там, где нужно, и ответ там, где ответ есть |
| citation | доля ответов со ссылкой `[n]` |
| lang_match | ответ на языке вопроса |
| invalid_citation_rate | доля ответов с номером цитаты вне `[1..N]` |
| latency | время ответа |

LLM-as-a-Judge (`src/evaluation/judge.py`, correctness 0–2 и faithfulness 0/1) реализован, но по умолчанию выключен:
локальная 3B-модель — ненадёжный судья, а 7B на CPU слишком медленная для всех экспериментов.

## 10. Результаты экспериментов

Методика: один фактор за раз от базовой конфигурации, на всех 38 вопросах. Полные таблицы со всеми метриками —
[`experiments/results/REPORT.md`](experiments/results/REPORT.md), CSV по каждой группе и `summary.json` по каждому варианту —
там же. Retrieval-эксперименты 1–4 сделаны без reranker и порогов, чтобы измерять «чистый» поиск.
Все retrieval-метрики считаются по 31 вопросу с ответом.

### 10.1 Стратегия chunking (800 символов, e5-small)

| Стратегия | chunks | Hit@1 | Hit@5 | Recall@5 | MRR |
| --- | ---: | ---: | ---: | ---: | ---: |
| fixed | 6 305 | 0.52 | 0.77 | 0.59 | 0.63 |
| overlap 150 | 7 815 | 0.48 | 0.84 | 0.62 | 0.63 |
| paragraph | 6 609 | 0.48 | 0.77 | 0.59 | 0.60 |
| **heading** | 7 964 | **0.65** | **0.87** | **0.64** | **0.75** |

Heading-chunking лучше по всем метрикам, MRR +0.12 к остальным. Причина: каждый chunk начинается с названия документа
и пути секции («Regulament ECTS | Articolul 5. ...»), поэтому даже короткий фрагмент сохраняет тему, а границы chunk
совпадают со смысловыми границами (статья регламента, раздел страницы). Paragraph проигрывает: на сайтах много
коротких абзацев-строк, они склеиваются в chunk без общей темы.

### 10.2 Размер chunk (heading)

| Размер | chunks | Hit@1 | Hit@5 | MRR |
| --- | ---: | ---: | ---: | ---: |
| 400 | 16 922 | **0.71** | 0.84 | **0.77** |
| **800** | 7 964 | 0.65 | **0.87** | 0.75 |
| 1200 | 5 415 | 0.55 | 0.84 | 0.67 |
| 1600 | 4 293 | 0.45 | 0.84 | 0.62 |

Чем больше chunk, тем «размытее» его вектор: Hit@1 падает монотонно с 0.71 до 0.45. Маленькие chunks точнее
ставят нужный документ первым, но чаще отрезают ответ от контекста (Hit@5 ниже) и вдвое увеличивают индекс.
Выбран **800**: лучший Hit@5 (для LLM важно, чтобы ответ был в контексте, а порядок поправит reranker) при MRR
почти как у 400.

### 10.3 Overlap (fixed, 800 символов)

| Overlap | chunks | Hit@1 | Hit@5 | MRR |
| --- | ---: | ---: | ---: | ---: |
| 0 | 6 305 | 0.52 | 0.77 | 0.63 |
| 100 | 7 247 | 0.55 | 0.81 | 0.66 |
| 150 | 7 815 | 0.48 | 0.84 | 0.63 |
| 200 | 8 477 | 0.55 | 0.81 | 0.67 |
| 400 | 12 891 | 0.52 | 0.81 | 0.64 |

Overlap помогает фиксированному окну (+4–7 п.п. Hit@5: ответ реже разрезается пополам), но эффект насыщается уже
на 100–200 символах, а overlap 400 удваивает индекс без выгоды. При этом даже лучший overlap уступает heading-chunking
(0.87 / 0.75), который решает ту же проблему без дублирования текста — поэтому overlap в итоговой конфигурации не используется.

### 10.4 Embedding-модели (heading-800)

| Модель | Размерность | Hit@1 | Hit@5 | Hit@10 | MRR | ctx_hit |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **multilingual-e5-small** | 384 | 0.65 | **0.87** | 0.87 | 0.75 | **0.87** |
| multilingual-e5-base | 768 | **0.71** | 0.81 | 0.84 | 0.75 | 0.81 |
| paraphrase-multilingual-MiniLM-L12-v2 | 384 | 0.61 | 0.84 | **0.97** | 0.70 | 0.77 |

Все три модели многоязычные (ro/en/ru). e5-base точнее на первом месте, но не лучше по MRR и хуже по Hit@5,
при вдвое большей размерности (вдвое больше памяти под индекс и медленнее кодирование). MiniLM интересен высоким Hit@10 (0.97):
он находит почти всё, но ранжирует хуже. Выбрана **e5-small**: лучший Hit@5 и ctx_hit, самая лёгкая.

### 10.5 Reranker (контекст LLM — 5 chunks в обоих случаях)

| | ctx_hit | ctx_MRR | ctx_precision | вопросы вне базы отсечены | время reranking |
| --- | ---: | ---: | ---: | ---: | ---: |
| только retriever | 0.87 | 0.75 | 0.30 | 0% | — |
| **retriever + reranker** | **0.90** | **0.77** | **0.50** | **86%** | 0.38 с |

Reranker поднимает долю релевантных chunks в контексте с 30% до 50% и возвращает в контекст один «потерянный» вопрос.
Ещё важнее — его score пригоден как порог «ответа в базе нет» (см. 10.7). Цена — 0.38 с на вопрос (20 пар).

### 10.6 Количество кандидатов K для reranker

| K | ctx_hit | ctx_MRR | ctx_precision | время reranking |
| ---: | ---: | ---: | ---: | ---: |
| 3 | 0.81 | 0.73 | 0.56 | 0.20 с |
| 5 | 0.84 | 0.76 | 0.52 | 0.18 с |
| 10 | 0.87 | 0.74 | 0.53 | 0.23 с |
| **20** | **0.90** | 0.77 | 0.50 | 0.37 с |
| 40 | 0.90 | **0.80** | 0.48 | 0.81 с |

Чем больше кандидатов, тем больше шансов, что reranker найдёт нужный chunk, стоящий у retriever'а далеко внизу.
Рост ctx_hit останавливается на K=20; K=40 чуть улучшает порядок, но вдвое дороже и пропускает больше вопросов вне базы
(среди 40 кандидатов чаще находится «похожий» chunk). Выбрано **K=20**.

### 10.7 Порог: cosine similarity vs score reranker'а

Распределение показало проблему: у e5 максимальный cosine для вопросов вне базы (0.80–0.87) почти совпадает с вопросами
с ответом (0.79–0.93) — модель «сжимает» оценки в узкий диапазон. Поэтому сравнивались два вида порога:

| Порог | ctx_hit (есть ответ) | вопросы вне базы отсечены |
| --- | ---: | ---: |
| нет | 0.90 | 0% |
| cosine ≥ 0.80 | 0.87 | 0% |
| cosine ≥ 0.83 | 0.87 | 14% |
| cosine ≥ 0.86 | 0.87 | 71% |
| reranker ≥ −2 | 0.90 | 57% |
| **reranker ≥ 0** | **0.90** | **86%** |
| reranker ≥ 2 | 0.87 | 86% |

Cosine-порог либо ничего не отсекает, либо начинает терять вопросы с ответом. Порог по score cross-encoder'а **≥ 0**
отсекает 6 из 7 вопросов вне базы, не теряя ни одного вопроса с ответом. Единственный пропущенный — «пароль Wi-Fi в библиотеке»:
в «Ghidul Studentului» действительно есть раздел про Wi-Fi в кампусе, и тут уже отказывается сама LLM.
В итоговой конфигурации: cosine ≥ 0.75 как дешёвый предфильтр + reranker ≥ 0.

### 10.8 LLM (одинаковый контекст, strict prompt)

| Модель | keyword_recall | ответы с цитатой | отказ вне базы | ложный отказ | время |
| --- | ---: | ---: | ---: | ---: | ---: |
| **qwen2.5:3b** | 0.72 | **0.94** | **1.00** | 0.16 | 7.6 с |
| llama3.2:3b | **0.73** | 0.81 | **1.00** | **0.10** | 7.7 с |

Время — на RTX 3050 4 GB (Ollama автоматически использует GPU). Обе модели ни разу не выдумали ответ на вопрос вне базы.
По полноте ответов они почти равны. Разбор ошибок по `per_question.jsonl`:

* 5 «ложных отказов» qwen распадаются на три разных случая: q18 и q27 — нужного документа нет в контексте (ошибка retrieval,
  и отказ здесь правильнее выдумки); q24 и q25 — модель **отвечает верно и затем дописывает фразу отказа**, метрика считает
  это отказом; и только q28 — настоящий отказ при ответе в контексте (таблица победителей CTF 2018 в виде сплошного текста);
* у llama нет поведения «ответ + отказ», отсюда её более низкий false refusal;
* llama чаще нарушает формат: ответ без цитат или ответ из одной ссылки `[3]` (q14).

Выбрана **qwen2.5:3b**: ссылки на источники в 94% ответов — главное требование к проверяемости RAG.

### 10.9 Prompt (qwen2.5:3b)

| Prompt | keyword_recall | ответы с цитатой | неверный номер цитаты | язык ответа = язык вопроса | отказ вне базы | ложный отказ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| basic | 0.75 | 0.00 | 0.00 | 0.95 | 0.86 | 0.03 |
| strict | 0.72 | 0.84 | 0.05 | 0.89 | **1.00** | 0.13 |
| **strict_v2** | 0.68 | **0.97** | **0.00** | **0.97** | **1.00** | 0.13 |

Basic-prompt даёт чуть более полные ответы и почти не отказывается, но не цитирует источники и на вопрос вне базы
пускается в рассуждения («The context provided does not contain any information about Wi-Fi passwords... It only mentions...»)
вместо явного отказа; на q28 он утверждает, что информации о CTF 2018 в контексте нет, хотя она там была.
Strict-prompt предсказуем: ответ с цитатами или одна фраза отказа, которую можно распознать программно.

**strict_v2 — доработка после ручного разбора ответов strict.** Проверка системы на живых вопросах показала три дефекта:

| Дефект strict | Пример | Причина | Исправление в v2 |
| --- | --- | --- | --- |
| Ответ не на языке вопроса (11%) | вопрос про Erasmus+ на английском → ответ на румынском | 3B-модель «перетекает» в язык контекста, правило в system prompt забывается | язык ответа — последней строкой сообщения пользователя; если ответ всё равно на другом языке — второй короткий вызов LLM «переведи, сохранив [n]» |
| Номер цитаты вне диапазона (5%) | «30 de ore [85]» при 3 источниках | модель копирует номер пункта регламента | в prompt явно указан диапазон `[1]-[N]`; в коде `sanitize_citations` удаляет номера вне диапазона |
| Противоречие источников | телефон декана 509907 | **не галлюцинация**: главная fcim.utm.md даёт 509907, страница «Decanul» — 509905; сайт противоречит сам себе | правило: при расхождении фрагментов приводить оба значения со ссылками |

Первая версия v2 (фраза отказа — последней строкой) сделала хуже: модель начала отказываться на вопросы с ответом.
Последняя инструкция для маленькой модели доминирует, поэтому фраза отказа перенесена в system prompt, а последней строкой
оставлен только язык ответа.

Итог: язык ответа 0.89 → 0.97, неверные номера цитат 5% → 0, ответы с цитатами 0.84 → 0.97, отказы вне базы по-прежнему 7/7.
keyword_recall снизился 0.72 → 0.68 — это разница в 1–2 вопроса из 31, в пределах шума (см. ниже). Выбран **strict_v2**.

Про шум: strict прогонялся дважды на одинаковой конфигурации — доля ответов с цитатами 0.94 в первом прогоне и 0.84 во втором
(temperature 0.1, недетерминированность GPU). Поэтому различия LLM-метрик меньше ~10 п.п. на этом наборе не стоит считать значимыми.

### 10.10 Короткие запросы и мягкий порог reranker

Проверка через веб-интерфейс выявила случай, которого не было в наборе вопросов: запрос одним словом.
На «магистратура» система отказывала, хотя нужный документ стоял первым:

| Запрос | Первый документ | score reranker |
| --- | --- | ---: |
| «магистратура» | Цикл II, Магистратура ✓ | −0.4 |
| «Что нужно знать о магистратуре?» | Цикл II, Магистратура ✓ | −2.9 |
| «Сколько длится магистратура?» | Организация обучения в магистратуре ✓ | +1.7 |
| «футбол» (вне базы) | случайный документ | −3.6 |

Cross-encoder обучен на парах «конкретный вопрос — абзац» (mMARCO) и занижает оценку ключевым словам и общим вопросам.
Порог 0 был подобран на 38 конкретных вопросах и для таких запросов слишком строгий. Решение — двухступенчатый порог:
score ≥ 0 — уверенный контекст; от −3 до 0 — контекст всё равно передаётся LLM, ответ помечается «низкая уверенность»,
и решение об отказе принимает модель по strict-prompt; ниже −3 — отказ без LLM, а пользователю показываются
похожие документы базы.

| Вариант (strict_v2) | отказ вне базы | ложный отказ | ответы с низкой уверенностью |
| --- | ---: | ---: | ---: |
| только порог 0 | 7 / 7 | 0.23 | — |
| **порог 0 + мягкий −3** | **7 / 7** | **0.19** | 0.08 |

Мягкий порог не пропустил ни одного выдуманного ответа на вопросы вне базы и вернул часть ложных отказов. Ложные отказы
здесь выше, чем в 10.9 (0.13) при той же конфигурации — это снова разброс между прогонами LLM.

## 11. Выводы

1. **Структура документа важнее размера окна.** Chunking по заголовкам с префиксом «название | секция» дал самый большой
   прирост из всех экспериментов (MRR 0.63 → 0.75). Overlap лечит тот же симптом — разрезанный ответ — хуже и ценой дублирования индекса.
2. **Больше модель — не значит лучше.** e5-base (768) не превзошла e5-small (384) на этом корпусе; MiniLM находит почти всё в top-10,
   но хуже ранжирует. Метрики нужно смотреть вместе: по одному Hit@1 был бы выбран e5-base, по Hit@10 — MiniLM.
3. **Reranker нужен не столько для порядка, сколько для фильтрации.** Он поднимает точность контекста с 30% до 50%, а его score —
   надёжный сигнал «ответа нет»: порог 0 отсекает 86% вопросов вне базы без потери ответов, тогда как cosine-порог у e5 практически
   бесполезен из-за сжатого диапазона оценок.
4. **Защита от hallucination — многоуровневая.** Пустой контекст → отказ без LLM; strict prompt → дословная фраза отказа;
   в итоге 7 из 7 вопросов вне базы получили отказ, ни одного выдуманного ответа.
5. **Метрики не заменяют чтение ответов.** Дефекты strict-prompt (язык, номера цитат) нашлись при ручной проверке, после чего
   для них появились метрики `lang_match` и `invalid_citation_rate`. А «неверный телефон декана» оказался не ошибкой модели,
   а противоречием в самих источниках — RAG честно воспроизводит качество данных.
6. **Слабые места**, найденные evaluation'ом: вопросы по нескольким документам (multi_doc: ответ собирается из 2–5 страниц,
   а в контекст часто попадает одна) и кросс-языковые вопросы к румынским регламентам (q27). Направления улучшения:
   гибридный поиск BM25 + векторы (точные термины вроде «n/a», «abs.»), query expansion / перевод вопроса на румынский,
   больше одного chunk на документ для multi_doc, OCR для трёх сканированных PDF.
7. **Ограничения оценки.** 38 вопросов — небольшая выборка: разница в один вопрос = 3 п.п., поэтому различия меньше ~5 п.п.
   для retrieval (например, overlap 100 vs 200) и меньше ~10 п.п. для LLM-метрик (повторный прогон того же prompt) не стоит считать значимыми. keyword_recall не видит перефразирование, а детектор отказа —
   «ответ + отказ» (поведение qwen); такие случаи разобраны вручную выше.
